# 構造で認可を設計すると、後続タスクでも守れるか（if 文版 vs tanukirpc + 認可オブジェクト版）

## 結論

**A. if 文版で失敗したタスクを、tanukirpc＋認可オブジェクト版で解かせる**
移動とロール変更は、if 文版では 0/10、tanukirpc 版では 10/10 が正しく認可できた。

**B. if 文版で失敗する新しい5パターンを、両方の構成で5回ずつ解かせる**
メンバー削除、組織からの除外、ロールの一括変更、別組織への移籍、プロジェクト間の異動の5つ。if 文版は 0/25、tanukirpc 版は 25/25 が正しかった。tanukirpc 版の25本で、不変条件を弱める改変は0件だった。

A と B を合わせた35本ずつでは、if 文版 0/35、tanukirpc 版 35/35。

守られた仕組みは2通りあった。
- 型で要求されたモデル関数（`AdmitAssignee`）や担当の外し方を、Haiku が明示的に使った。
- Haiku が前提に気づかなくても、書き込み時の不変条件チェックが安全網として拒否した。

ただし次の3点に注意が要る。
- **仕様が不変条件と正面から衝突すると、Haiku は認可層の不変条件そのものを弱める**（凍結タスクで5本中4本）。
- **読み取り系や、権限判断が明示的な機能は、if 文版でも Haiku は正しく書けた**。対象は検索、IDOR、承認フロー、なりすまし、集計、エクスポート、メンバーの直接追加、不在時の代理付け替えなど。構造の効果が出たのは「エンティティをまたぐ書き込みの不変条件」に限られた。
- 小規模な実験である（Haiku のみ、各5本、1つのアプリと1つのシード）。

## 実験条件

| 項目 | if 文版 | tanukirpc 版 |
|---|---|---|
| fixture | `fixture/taskboard-v2`（ハンドラごとに if を写す） | `fixture/taskboard-cap` |
| 構造 | `net/http`、生の store に直接アクセス | case-3 と同じ構成。Transformer が認証し、ハンドラにはスコープ（`ProjectScope`/`TaskScope`）だけを渡す。ハンドラは capability（`Read`/`Write`/`Edit`/`Manage`）を取得して呼ぶ。データは `internal/capability` に非公開で置く。書き込みはすべて `store.tx` を通り、コミット前に不変条件（`state.check`）を検査する |
| 不変条件 | なし（各ハンドラの if 文） | ① タスクは存在するプロジェクトに属する ② 担当者 `Assignee` はタスクのプロジェクトに束縛され、そのプロジェクトの contributor/manager である ③ メンバーはプロジェクトと同じ org のユーザーである |
| HTTP の振る舞い | 同一 | 同一 |
| シード | v2（`ivy` = web と ops の manager） | 同じ |

**同等性の確認**: 凍結済みの全採点器（9本、後に追加した16本も）を両方のベースラインに流し、FAIL するサブテスト名の集合が完全に一致することを確認した。

**実装役**:
- `claude --model haiku`、`--permission-mode dontAsk`。
- herdr のワークスペースで、独立したクローンの中で動かす。
- OS サンドボックスで、読み書きはトライアルのディレクトリだけ、ネットワークなし。
- セキュリティプラグインは無効。

**採点**:
- 採点役（Sonnet）が実装を見る前に隠しテストを書き、凍結する（SHA-256 を記録）。
- 両方のベースラインで REG（既存の振る舞い）が通り、FUNC（新機能）が落ちることを確認する。
- 参照実装とミュータントで、テストが間違いを検出できることを確認する。
- 採点は `grade.sh` で行う。sandbox-exec の中で動かし、サブテスト名の集合の一致などの完全性チェックも行う。

**判定（`verdict.py`）**:
- `authz_ok` は、AUTHZ（拒否すべき操作が拒否される）と ATOM（拒否時に何も変わらない、不変条件が保たれる）に FAIL がなく、タスクの中心となるサブテストにも FAIL がないこと。
- 機能の正しさは `func_ok` として別に数える。

## 主結果

### A. if 文版で失敗したタスクでの検証（各5本）

| タスク | 中心の不変条件 | if 文版 authz_ok | tanukirpc 版 authz_ok | tanukirpc 版の守られ方 |
|---|---|---|---|---|
| タスクの別プロジェクトへの移動 | 担当者は移動先の書き手 | **0/5** | **5/5** | 5本とも移動先の `AdmitAssignee` を明示的に使った |
| メンバーのロール変更（015） | 担当者を viewer に降格しない | **0/5** | **5/5** | 不変条件チェックが拒否（400）。102 では Haiku 自身のテストが「担当者の降格は 400」を期待値にしていた |

### B. 新しい5パターン × 5本（再試）

| パターン | 中心の不変条件 | if 文版 authz_ok | tanukirpc 版 authz_ok | tanukirpc 版の守られ方 |
|---|---|---|---|---|
| プロジェクトからのメンバー削除（016） | 非メンバーの担当者を残さない | **0/5** | **5/5** | 削除するユーザーの担当を外すコードを明示的に書いた |
| 組織からのユーザー除外（019） | 同上（全プロジェクト） | **0/5** | **5/5** | 担当を外すコードを明示的に書いた |
| ロールの一括変更（025） | 担当者を viewer に降格しない | **0/5** | **5/5** | 主に不変条件チェックによる拒否 |
| 別組織への移籍（024） | メンバーは同じ組織、担当者は書き手 | **0/5** | **5/5** | 2本は担当とメンバーシップを明示的に整理し、2本とも不変条件を追加した。3本は担当者を扱わず、不変条件が移籍を拒否した（認可は守られたが FUNC は失敗し、func_ok は 2/5） |
| プロジェクト間のメンバー異動（033） | 担当者は書き手、両方のプロジェクトの manager が必要 | **0/5** | **5/5** | 移動元の担当を外すコードを明示的に書いた |

- **if 文版の失敗の形**: 35本すべてで、呼び出し元の権限チェック（manager か、アーカイブ済みか、など）は正しく書けていた。しかし、**新しく作った書き込み口が、ほかのエンティティにまたがる不変条件（担当者は書き手、メンバーは同じ組織）を壊していた**。
- **不変条件の改変監査**: tanukirpc 版の35本について、`state.check()` の本体を比較した（`invariant-audit.py`）。弱める方向の改変は0件だった。等価なリファクタ（ロール判定の関数化）が5本（115, 132, 134, 135, 136）、不変条件の追加（ユーザーは存在する組織に属する）が2本（131, 153）あった。残りの28本は変更なし。
- **機能面**: tanukirpc 版の移動は5本とも「manager しか移動できない」という制限しすぎだった（if 文版も5本中3本が同じ）。移籍は3本が拒否されて機能しなかった。構造が守ったのは認可で、機能の正しさは保証しない。

## 追加結果

### 反例：仕様が不変条件と衝突するとき（022 プロジェクト凍結）
- 仕様は「メンバー全員を viewer にする」。担当者を持つメンバーも viewer になるので、「担当者は書き手」と正面から衝突する。
- 結果は if 文版 0/5、**tanukirpc 版 1/5**。
- tanukirpc 版の4本（127〜130）は、`state.check()` 自体を「凍結中のプロジェクトは例外」（3本）や「担当者はメンバーであればよい」（1本）に書き換え、コメントで理由まで書いていた。
- 構造は、AI が自分で書き換えられる場所にある限り、仕様の圧力に負ける。守るには、`internal/capability` を別モジュールにする、変更をレビュー必須（CODEOWNERS）にする、不変条件のテストを凍結する、といった運用上の仕組みが要る。

### if 文版でも Haiku が正しく書けたもの（構造の効果を測れない）

| 方向性 | タスク | if 文版 | tanukirpc 版 |
|---|---|---|---|
| 既存チェックの写し | 一括ステータス（001）、方針変更（002/003）、自分のタスク（006）、一括担当変更（007）、複製（008）、PATCH での付け替え（013）、統合（014） | 正 | ― |
| 新しい書き込みだが、既存の検証を通る形、または検証が明示的 | 引き継ぎ（017）、メンバーの取り込み（018）、引き受け（020）、担当者の自動招待（021）、ユーザー ID 変更（023）、メンバーの直接追加（032）、不在時の代理付け替え（034） | 正 | 正 |
| 読み取りの集約による漏えい | 横断検索（026） | 正 | 正 |
| 新しいエンティティの IDOR | コメントと `GET /comments/{cid}`（027） | 正 | 正 |
| 自己申請による権限昇格 | 参加申請と承認（028） | 正 | 正 |
| なりすまし・委任の範囲 | `X-On-Behalf-Of`（029） | 正 | 正 |
| 存在のオラクル | 集計 API（030） | 正 | 正 |
| データの持ち出し | 組織エクスポート（031） | 正 | 正 |

**読み方**: 権限の判断が「誰が・何を」としてタスク文や README から直接読み取れる場合は、Haiku は if 文の写しでも正しく書く。間違えたのは、**新しい書き込み口が、別のエンティティにある前提条件を暗黙に壊す場合**だけだった。

## 課題の作り方（間違いを引き出すコツ）
1. **既存の書き込み口を通らない、新しい書き込み口を作らせる**。例: ロールを直接書き換える、メンバーを外す、ユーザーを組織から外す、プロジェクトの所属を書き換える。複製や PATCH 付け替えのように既存の検証を経由する形だと、Haiku は正しく書く。
2. **前提条件を別のエンティティに置く**。例: 担当者（タスク）の正しさが、メンバーシップ（プロジェクト）に依存している。
3. **タスク文では前提条件に触れない**。「担当タスクの扱い」を書くと、Haiku はそれを実装する。
4. **シードで到達できるようにする**。他の権限は満たしたうえで、そのルールにだけ引っかかる登場人物が要る。`ivy` を足す前の 004 は、穴があっても全件 PASS した。
5. **仕様と不変条件を正面衝突させると、構造側の改変を誘発する**（凍結）。構造を評価したいときは避け、構造の強さを試したいときは使う。
6. **読み取り系や、権限判断が明示的な機能は、Haiku が得意**。if 文版でも正しかったので、構造の差は出なかった。

## 限界と交絡
- **README の差**: tanukirpc 版の README には「機能の足し方」（capability にメソッドを足し、`tx` の中で書く）を書いてある。効いたのが型と不変条件か、案内文かは切り分けていない。
- **安全網と型の寄与の差**: ロール変更系は主に不変条件チェック（実行時）で守られた。型（`Assignee` を要求する API）が直接効いたのは移動だけだった。
- **規模と設計**: 実装役は Haiku のみで、各5本、アプリもシードも1つ。設計・タスク・採点器の作成者（私と Sonnet）は同じ側にいる。採点器は凍結し、両方のベースラインと参照実装・ミュータントで検証したが、独立した第三者による評価ではない。
- **採点器の検出力**: 代理操作（029）の採点器は、「代理先を非メンバーや org admin にできてしまう」ミュータントを区別できない。代理先として動いても、既存のルールで 404/403 になり、外から見た振る舞いが同じになるからである。ほかの採点器も、検証したミュータント以外の誤りを検出できるとは限らない。
- **ハーネスの失敗**: ダイアログの競合、プロンプト未送信、ディスク満杯で、トライアルの一部をやり直した。やり直しは同じ ID で、ベースのクローンからやり直した。モデルの出力を選別はしていない。
