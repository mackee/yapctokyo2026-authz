# 初期のトライアル 001〜015: 素朴な `if` 文チェーンのアプリに対する Haiku

この実験では、小さなコーディングエージェント（Claude Haiku）が、**各ハンドラに `if` チェックを手でコピーして認可を実装している素朴なコードベース**を変更するときに、リソース単位の認可を誤る例を探す。

手順、スクリプト、落とし穴は Claude Code のスキルとしてまとめてある:
[`.claude/skills/haiku-attempt/SKILL.md`](../../.claude/skills/haiku-attempt/SKILL.md)。

## 中身

| パス | 内容 |
| --- | --- |
| `fixture/taskboard/` | ベースラインのアプリ: Go の `net/http`、in-memory のシード、`X-User` による本人確認、ルールは README に記載 |
| `tasks/` | Haiku にそのまま渡したタスク文 |
| `results/NNN/` | トライアルごとの凍結済みの隠し採点器、`run.sh`、サマリ、分析 |
| `.claude/skills/haiku-attempt/` | スキル、`scripts/run-trial.sh`、`scripts/setup-base.sh`、採点器のプロンプト |

パスはリポジトリのルートからの相対パスである。トライアル自体はこのリポジトリの外、`~/src/haiku-probe/{base,trials}` で実行する。
これにより、Haiku が共有された git オブジェクトを通じてほかの実験を読むのを防ぐ。

## ここまでの発見

- **再現する唯一の誤りは、*コピー*ではなく*移動*にある。** 移動先のルール「担当者はそのプロジェクトの contributor か manager でなければならない」は、移動の2つのトライアル（シード v1 の 004、シード v2 の 005）の両方で抜けた。コピー（008）では保たれた。
  コピーはタスクの*作成*として捉えられるので、Haiku は `createTask` のチェックを担当者ルールも含めて丸ごとコピーした。移動は*フィールドの変更*（`task.ProjectID = ...`）として捉えられるので、更新側とプロジェクトのチェックをコピーした。作成時だけの担当者ルールは一緒に来なかった。004 では Haiku はこの抜けを名指しし、意図した動作として文書化までした。005 では Haiku 自身のテストが誤った振る舞いを表明している。
- **シードの網羅性が、採点器に見えるものを決める。** シード v1 では移動の欠陥に到達できなかった（133/133 合格）。ユーザーを1人（`ivy`）足すと、4つのテストで落ちた。採点器を設計するときは、どのルールにも、それ以外の権限は有効なまま到達できるアクターが少なくとも1人いることを確かめること。
- **`if` 文チェーンを丸ごとコピーするやり方は、おおむねうまくいく。** 一括ステータス更新、組織 admin のポリシー変更、自分のタスク、担当者の一括変更、コピーはすべて正しかった。新しいハンドラを足すたびにルールのコピーが1つ増える（現在は最大5つ）。これは保守上のリスクだが、採点器は測っていない。
- Haiku は仕様が何も言っていないところで**制限しすぎる**ことがある（005: manager 限定の移動）。これは安全だが機能的には誤りであり、認可の穴とは別に採点している。
