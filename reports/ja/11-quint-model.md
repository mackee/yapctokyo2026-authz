# 追加実験: 仕様と不変条件を Quint でモデル化しておくと、どうなるか（2026-11-26）

## 動機

「形式検証すればいいのでは」という質問を想定した。そこで、仕様と不変条件を Quint で書いてリポジトリに置き、2つの使い方を比べた。

- A: モデルを置いておくだけ
- B: エージェントに、モデルの更新と検査を必須にする

不変条件が崩れるケース（降格、凍結など）でどうなるか、拒否しすぎ（移動）が緩和されるかを見る。

## 条件

### モデル: `fixture/quint/taskboard.qnt`（if 版と rel 版で同一）

- 状態: users、projects、members、tasks。初期状態は README の seed と同じ。
- 既存の4操作（閲覧・作成・更新・削除）を、それぞれ次の組で書いた。
  - outcome 関数: 返すべき HTTP ステータスを決める
  - アクション: 2xx のときだけ状態を変える
- 中身は README のアクセス規則と、if 版のチェックの順序どおり。
- 不変条件は README-rules と同じ3つ。
  - `inv_taskInExistingProject`: task は存在する project に属する
  - `inv_assigneeIsWriter`: 担当者はその project の contributor か manager
  - `inv_memberInProjectOrg`: メンバーはその project の org に属する
- seed の例を確かめる `quint test` を16件付けた。
- 動作確認:
  - `quint typecheck` / `test` / `run --invariant=invariants` が、ネットワークも `$HOME` もないサンドボックス内で通る。
  - 降格を素朴にモデル化した版では、3回中3回とも違反が出た。

### フィクスチャとタスク文

- `taskboard-{v2,rel}-sql-quint`:
  - 元のフィクスチャに `spec/taskboard.qnt` を足し、README の末尾に「Formal model」の節を加えた。
  - 節に書いたのは、モデルの説明と検査コマンドだけ。不変条件を英語では書いていない。
  - Go のコードは同一。
  - rel 版の README には、もともと英語の不変条件がある。
- A（置くだけ）: タスク文は元のまま（`tasks/`）。比較相手は最初の比較（441〜605）。
- B（更新と検査を必須にする）: `tasks/quint/`。元の文に、次の1文を足した。
  > 実装の前に、spec/taskboard.qnt にこの操作の outcome 関数とアクションを追加して step から選ばれるようにし、quint run spec/taskboard.qnt --invariant=invariants で違反が出ないことを確かめてください。実装はモデルに合わせてください。

### 環境とハーネス

- Quint 0.33.1 を `/Users/Shared/quint` に置いた。
  - node 本体と Rust の評価器も同じ場所に置き、`QUINT_HOME=/Users/Shared/quint/home` とした。
  - 試行内からは `/Users/Shared/quint/bin/quint` で実行する。
- `run-trial.sh` の `QUINT_BIN` を指定したときだけ、quint の実行を許可した。
  - あわせて、環境メモに「quint はこのパスで実行できる」という1行を足した（`env-note-quint.md`）。
  - この1行は A にも B にも入る。

### 試行

8タスク × 2版 × A/B × Haiku/Sonnet × 5回 = 320本。ユーザーが内容を承認した。

| 条件 | v2 Haiku | v2 Sonnet | rel Haiku | rel Sonnet |
|---|---|---|---|---|
| A 置くだけ | 1128〜1167 | 1168〜1207 | 1208〜1247 | 1248〜1287 |
| B 更新と検査 | 1288〜1327 | 1328〜1367 | 1368〜1407 | 1408〜1447 |

- 320本すべてで driver ログが DONE で終わり、モデルの取り違えもなかった。採点では320本すべてが valid_run だった。
- 7本は quint の出力ファイル（`out.itf.json` など）を未追跡のまま残していた。コミットはされているので有効とした。

## 読み取れること

### 1. 不変条件の漏れは、モデルの更新と検査を必須にするとほぼ消えた

- B は4セルとも、凍結を除いて 35/35 だった。最初の比較で 1/35 だった if × Haiku も 35/35 になった。凍結を含めても 38〜40/40 だった。
- これは英語で不変条件を書いた効果（README-RULES、降格系で Haiku 7/10、Sonnet 5/10）より大きい。
- ただし、効いたのは反例のフィードバックではなかった。
  - B の160本のうち、違反を見たのは20本だけだった。ほとんどの試行は、モデルにアクションを書く段階で「担当を外す」か「拒否する」ガードを最初から入れていた。
  - 不変条件が「満たすべき式」として目の前にあり、それに対して新しいアクションを書かせたこと自体が効いた、と読める。
- A（置くだけ）でも、if 版は大きく伸びた（Haiku 1→18、Sonnet 23→33）。
  - A でモデルを変更しなかった試行にも合格が多い（if × Haiku は15/32）。モデルを読んだだけでも、不変条件の記述として効いている。

### 2. 拒否しすぎは減らなかった。拒否しすぎは、モデルの中に書かれていた

- 拒否しすぎは、最初の比較 16、A 22、B 19 だった。正常系の文を足した条件（2）のようには減らない。
- 移動のモデルを書いた28本（A と B の合計）では、モデルの方針と func の結果が28本すべてで一致した。
  - モデルの `moveOutcome` が「manager でなければ 403」（移動元で。移動先でも求めるものもあった）なら func 失敗（21本）。
  - 「contributor は自分のタスクなら可」なら func 成功（7本）。
- つまり、実装はモデルどおりだった。拒否しすぎはモデルを書く段階で決まっていた。
- 不変条件の検査は「起きてはいけない状態」しか見ない。だから、拒否しすぎのモデルは検査を素通りする。

### 3. 検査は、モデルが仕様どおりかまでは保証しない

- **凍結では、不変条件のほうを緩める例があった。多くは反例を見る前に緩めていた。**
  - 凍結で不変条件の定義を書き換えたのは8本（A 5本、B 3本）。書き換え方は2通りだった。
    - `inv_assigneeIsWriter` を `inv_assigneeIsMember` に変えた（担当者はメンバーなら viewer でもよい）。
    - 凍結済みプロジェクトを例外にした。
  - 8本すべてが authz で落ちた。凍結済みプロジェクトに担当者が残っていた。
  - `quint run` で違反（反例）を見ていたのは、8本のうち 1151 と 1352 の2本だけだった（`results/quint-usage.tsv`）。残り6本は、反例を見る前から不変条件を書き換えていた。
  - 1352（B、Sonnet）の最終報告は次のとおり。「最初のモデル実行で inv_assigneeIsWriter が破れた。……頼まれていないし、データを失うので、凍結時に担当は外さなかった。代わりに、凍結したプロジェクトも受け入れるよう不変条件を緩めた」
  - 不変条件を変えずに凍結をモデル化した23本のうち、22本は authz_ok だった。
- **不変条件にない規則は、モデルから抜けても捕まらない。**
  - 1310（B、Haiku、凍結）は、モデルの `freezeOutcome` でアーカイブ済みのチェック（409）を落としていた。
  - 実装もそのとおりになり、`AUTHZ_ArchivedManagerAnn_legacy` で落ちた。アーカイブは不変条件に入っていないので、`quint run` では見つからない。
- まとめると、モデルと実装の間のずれはほぼ見られなかった。B の authz 失敗は、凍結の4本だけだった（不変条件を緩めた 1311、1351、1352 と、アーカイブ済みのチェックが抜けた 1310）。誤りはどれも、モデルそのもの（どの不変条件を守るか、何を拒否するか）に入っていた。

### 4. Haiku でも Quint は書けた

- B の Haiku 80本は、すべてモデルにアクションを足し、`quint run` を実行してコミットまで進んだ。
- 型エラーや構文エラーで止まったままになった試行はなかった。

## そのほか

- 移籍（transfer）の func_ok は、rel 版では A でも B でも少し下がった。
  - rel × Haiku: 最初の比較 4/5 → A 2/5、B 2/5
  - rel × Sonnet: 5/5 → A 4/5、B 4/5
  - if × Haiku では、逆に 0/5 → A 1/5、B 4/5 に上がった。
  - 1セル5本なので、原因はまだ調べていない。
- 「権限で拒否された」は B の8本で計13回あった。パイプ付きなど、許可された形以外の quint コマンドを打った試行で、エージェントは許可された形で打ち直していた。

## 注意

- 各セルは5本しかない。
- モデル、フィクスチャ、タスク、採点器は同じ側が作った。
  - モデルの不変条件は、採点器が見る ATOM と同じ内容を式で書いたものだ。正解に近い情報を渡している点は、README-rules と同じ。
- `quint run` はランダムシミュレーションで、網羅的な検査ではない（Apalache を使う `quint verify` は使っていない）。
- A と B の両方に、「quint が使える」という環境メモが入っている。A を「何も言わずに置いただけ」とは言い切れない。
