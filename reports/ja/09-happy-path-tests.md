# 追加実験: 正常系の table driven test と正常系の仕様文で、拒否しすぎは減るか（2026-11-24）

## 動機

最初の SQLite 比較（441〜605）では、タスクの移動で15本が拒否しすぎだった。「contributor が自分のタスクを移動する」のも 403 にしていて、AUTHZ は通るが FUNC は落ちる。仕様は守れていても、機能としては動いていない。

ユーザーの仮説は「正常系のテストがベースにあれば、AI がそれに倣い、拒否しすぎに気づく」。依頼元はスライド側セッション（yapc2026tokyo-65）。

## 条件

最初の比較から、次の3点を同時に変えた。

1. **ベースに正常系テストを追加した。**
   - `fixture/taskboard-{v2,rel}-sql-happy` は、元の fixture に `allowed_test.go` を足しただけ（`results/happy-allowed_test.diff`。両版で同一）。
   - `TestAllowed` は許可側だけの table driven test で、17行ある。ロール×操作（閲覧・作成・更新・削除）の行が並び、ステータスコードだけを確かめる。
   - 冒頭のコメントは "When you add an operation, add a row for every role that should be allowed to perform it."。
   - 既存の、許可と拒否が混ざったテスト（TestCreate など）はそのまま残した。
   - README の不変条件の置き方は最初の比較と同じ（rel 版にあり、if 版になし）。
2. **タスク文で正常系を明示した。**
   - 8タスクすべてに、許可側だけを述べる文を1つ足した（`tasks/happy/`、差分は `results/happy-tasks.diff`）。
   - 文の内容は、凍結済み採点器の FUNC テストで実際に操作している人に合わせた。
   - 例（移動）: 「移動元と移動先の両方で contributor か manager のユーザーは、自分が担当のタスクを移動できます。両方で manager のユーザーは、誰が担当のタスクでも移動できます。」
3. **「テストも追加し、」を外した。**「go test ./... が通る状態で git commit」は残した。

ベースのテスト、タスク文、試行の規模はユーザーがレビューして承認した。

採点器の同値性も確かめた。graders-200 の8本を、元のベースと -happy のベースの両方で走らせ、失敗した項目の集合がすべて一致した。-happy ベースの自前テストは56本すべて通り、integrity も OK だった。

試行: 8タスク × 2版 × Haiku/Sonnet × 5回 = 160本。

| 版 | Haiku | Sonnet |
|---|---|---|
| v2-sql-happy | 646〜685 | 686〜725 |
| rel-sql-happy | 726〜765 | 766〜805 |

160本すべてで driver ログが DONE で終わった。モデルの取り違えや未コミットの変更はなく、160本とも valid_run だった。

結果のファイル:
- 対応表: `results/{v2,rel}-sql-happy-{haiku,sonnet}-manifest.tsv`
- 判定: `results/*-happy-*-verdicts/verdicts.jsonl`
- 試行ごとの diff・サマリ: `results/structure/trials/{646..805}.*`
- テスト行の集計: `results/happy-testrows.tsv`

## 結果

### 凍結を除く7タスクの合計（/35）。数字は「最初の比較 → 今回」

| 版 × モデル | authz_ok | func_ok | 拒否しすぎ（authz 通過・func 失敗） |
|---|---|---|---|
| if × Haiku | 1 → 0 | 28 → 32 | 0 → 0 |
| if × Sonnet | 23 → 19 | 28 → **35** | 5 → **0** |
| rel × Haiku | 29 → 27 | 29 → 33 | 6 → 2 |
| rel × Sonnet | 35 → 35 | 30 → **35** | 5 → **0** |

### 移動（/5）

| 版 × モデル | authz_ok | func_ok | 拒否しすぎ |
|---|---|---|---|
| if × Haiku | 1 → 0 | 3 → 5 | 0 → 0 |
| if × Sonnet | 5 → 2 | 0 → 5 | 5 → 0 |
| rel × Haiku | 5 → 5 | 0 → 5 | 5 → 0 |
| rel × Sonnet | 5 → 5 | 0 → 5 | 5 → 0 |

### そのほかの変化

- rel × Haiku:
  - 移籍は func 4→3、拒否しすぎ 1→2 だった。`FUNC_TransferAnnManagerAllThree` で落ちている。アーカイブ済みプロジェクトのメンバーの扱いが原因で、最初の比較にも同じ失敗があった。
  - ロール変更は authz 4→3、一括変更は 2→0、メンバー異動は 4→5 だった。
- if × Sonnet: ロール変更は authz 2→0、削除は 5→4、一括変更は 0→1、除外は 1→2 だった。
- 凍結: 変化なし（if 0/0、rel は Haiku 0、Sonnet 1）。

## 読み取れること

- **移動の拒否しすぎは 15本 → 0本になった。** 4セルすべてで、移動の func_ok が 5/5 になった。全体でも、拒否しすぎは 16本 → 2本に減った。
- **ただし、テストが拒否しすぎを捕まえたのではない。**
  - 160本のトランスクリプトのどれにも、途中の `go test` で `--- FAIL: TestAllowed` が出た記録はない（エージェントの会話記録から数えた。会話記録は公開していない）。
  - 最初から拒否しすぎない実装を書いていた。効いたのは「誰に何を許すか」を書いた正常系の仕様文か、テーブルを読んで得た期待のどちらかで、テストの失敗によるフィードバックではない。今回の設計では、この2つを分けられない。
- **AI はテーブルに行を足した。足したのはすべて正常系の行だった。**

  | 版 × モデル | 行を足した試行 | 足した行 |
  |---|---|---|
  | if × Haiku | 39/40 | 75行 |
  | if × Sonnet | 38/40 | 89行 |
  | rel × Haiku | 40/40 | 86行 |
  | rel × Sonnet | 30/40 | 75行 |

  - `TestAllowed` に拒否側（2xx 以外）の行を足した試行は、0本だった。
  - 移動の試行では、20本中18本が「contributor が自分のタスクを移動する」行を足した。
  - 「テストを書け」と指示しなくても、160本すべてが別のテスト関数も書いた。そこでは拒否側（400/403/404/409）も確かめていた。
- **不変条件（ATOM）は、if 版でむしろ漏れが見えるようになった。**
  - if × Sonnet の移動は authz 5→2 だった。今回の失敗3本（686、687、690）と、if × Haiku の5本（646〜650）は、すべて `ATOM_IvyAssigneeNotWriterInDest` で落ちている。manager が、担当者が移動先で書き手でないタスクを移動できてしまうケースだ。
  - 最初の比較の if × Sonnet は、manager の移動まで拒否していたので、この漏れが隠れていた（vacuous pass）。機能が動くようになって、不変条件の穴が表に出た。
  - rel 版では、移動の ATOM は Haiku も Sonnet も 5/5 のままで、表に出た漏れはない。不変条件が README と集約にあるためと考えられる。
- **テストを足したことで不変条件が悪くなった、という明確な証拠はない。**
  - 降格系（ロール変更と一括変更）で数本の増減はあった。if × Sonnet の 2/10→1/10（ロール変更 2→0、一括変更 0→1）、rel × Haiku の 6/10→3/10 など。
  - 1セル5本なので、ノイズと区別できない。降格系の失敗パターン（担当を扱わない）は、最初の比較と同じだった。

## 注意

- 最初の比較から3つを同時に変えた。ベースのテスト、正常系の仕様文、「テストを書け」の削除だ。差は合成効果としてしか読めない。
  - 次に切り分けるなら、「正常系の文だけ」と「テストだけ」の2条件を足す。
- 各セルは5本しかない。
