# 実運用寄せの fixture と SQLite 版（2026-11-24）

## fixture

- **`taskboard-rel`**（コミット a121261、トライアル 401〜440）: 実運用の書き方に寄せた in-memory 版。
  - tanukirpc が型付きのリクエストボディをデコードし検証する。400 は認可より先に返る。
  - タスクの作成は 200 を返す。
  - Transformer が認可オブジェクト（`ProjectAuthz` / `TaskAuthz`、`CanWrite` / `CanEdit` / `CanManage` …）を作る。
  - DB アクセスは `*Table`（`Find` / `List*`、`ErrNoRows`）と行オブジェクトに隠す。
    - 関係メソッドは `(ctx, db)` を取る。
    - 行の変更メソッドは非公開。
  - API の操作は `TaskTable.Create(ctx, db, authz, input)` の形。
  - 全体チェックはない。
- **`taskboard-v2-sql`**（トライアル 441〜480）: if 文版を SQLite にしたもの。
  - ハンドラが `*sql.DB` に生 SQL を投げ、権限はコピーした if 文で確かめる。
  - 作成は 200 を返す。
- **`taskboard-rel-sql`**（トライアル 481〜520）: `taskboard-rel` の構成のまま、データ層を `database/sql` と生 SQL にしたもの。
  - `DB` は `*sql.DB` または `*sql.Tx`。トランザクションは `inTx`。
  - 「担当者は書き手」の DB 制約は入れていない。
- **採点**: `results/structure/graders-200/` を使った。元の採点器からの変更は2点だけ。
  - タスク作成の期待値を 201 → 200 にした。
  - ロール観測の試行のボディを、有効な値にした。
- **同等性**: 3つの fixture とも、8つの採点器すべてで、元の採点器を if 文版に流した結果と一致した（`results/structure/equivalence-{rel2,v2-sql,rel-sql}/`）。
- **再実行**: エージェントが起動しなかった5本は、別の番号で回し直した（`results/rerun-replacements.txt`）。120本すべて valid_run。

## 読み取れること

- **SQLite にしても結果は変わらない。**
  - if 文版は SQL でも 1/35。444 だけが移動で合格した。
  - 関係メソッド版は mem 30/35、SQL 29/35。
  - 失敗はどれも「担当が残る」形で、500 などの基盤由来の失敗はなかった。
- **実運用寄せにしても、構造の性質は変わらない。** 旧 rel 30/35、新 rel 30/35。
- **パターンへの追従は完全だった。** 降格系と、SQL 版の失敗2本（499、519）の計22本すべてが、新しい操作を `*Table` のメソッドとして書いた（`MembershipTable.ChangeRole` / `SetRole` / `UpdateRoles` / `RemoveFromOrg` / `Move` など）。
- **成否は `AssignedTasks`（担当の読み込み）を呼んだかどうかで完全に分かれる。**
  - 22本すべてで一致した。旧 rel の10本と合わせると32本で一致。
  - 一括変更はどの版でも 1〜2/5 だった。起点（Project）から2段たどる必要があるパターンは、構造があっても漏れる。
- **凍結は、全体チェックのない版ではどれも 0/5（全体チェックのある cap 版だけ 1/5）。** 全体チェックがないので、不変条件を弱める改変すら必要なく、担当者に触れずに通ってしまう。
