# 追加実験: 不変条件のテストを置く、TDD を指示する（2026-11-26）

## 動機

スライドの「効果があったものの表」で、「テストを置く」列の2マスがまだ試していなかった。

- 不変条件 × テスト
- 要件とのぶつかり（凍結）× テスト

想定質問「不変条件のテストを置けば済む？」「TDD なら？」にも答えるため、次の3条件を比べた。

| 条件 | fixture | タスク文 |
|---|---|---|
| ① 不変条件ヘルパー | `taskboard-{v2,rel}-sql-invtest` | 元のまま（`tasks/`） |
| ② TDD | 元の `taskboard-{v2,rel}-sql` | `tasks/tdd/` |
| ③ TDD + ヘルパー | `taskboard-{v2,rel}-sql-invtest` | `tasks/tdd/` |

## 条件

### ① 不変条件ヘルパー（`taskboard-*-sql-invtest`）

- `rules_test.go`（新規）
  - `checkModelRules` が、3つの規則を SQL で確かめる。
  - 破れていれば、どの規則がどう破れたかを出す。例: `after PATCH /projects/web/tasks/t2: model rule "an assignee is a contributor or manager of the task's project" is broken: task t1 in web is assigned to ben, whose role there is viewer`
  - 規則の文言は rel-sql の README と同じ。
    - tasks belong to existing projects
    - an assignee is a contributor or manager of the task's project
    - project members belong to the project's organization
  - `TestSeedKeepsModelRules` を1件足した。
- `main_test.go`
  - 共通ヘルパー `do()` が、GET 以外のリクエストのたびに `checkModelRules` を呼ぶ。
  - 新しい操作のテストを `do()` で書けば、チェックが自動で走る。
- `main.go`
  - テストから DB を見るために、`newServer` の戻り値を `appHandler{Handler, db}` で包んだ。
  - HTTP の振る舞いは変わらない。
- README は変えていない。
  - v2-sql の README には、もともと不変条件がない。そのため v2-sql では、不変条件がテストの中にしか出てこない。
  - rel-sql の README には、もともと同じ規則がある。
- 外形（HTTP だけ）で作る案も検討した。今の API にはメンバーやロールを見るエンドポイントがない。そのため外から確かめられるのは担当者の規則だけで、3規則を確かめられる DB 版を採った（ユーザー承認）。
- 確認したこと:
  - 凍結済みの採点器 8個 × 2版で、元の fixture と失敗するサブテストがまったく同じ（`results/structure/equivalence-*-sql-invtest/`）。
  - 違反を注入すると、3規則とも検出する。

### ② TDD（`tasks/tdd/`）

元のタスク文の最後の1文「テストも追加し、go test ./... が通る状態で git commit してください。」を、次の文に置き換えた。

> テスト駆動で進めてください。実装の前に、この機能に期待する振る舞いを確かめるテストを書き、go test ./... でそのテストが失敗することを確かめて、その時点で一度 git commit してください。それから実装し、go test ./... が通る状態でもう一度 git commit してください。

- 拒否側のテストや不変条件のテストを書け、とは言っていない（答えを教えないため）。
- 失敗するテストを先にコミットさせたので、テストが先に書かれたかを差分から確かめられる。

### 1. 不変条件のテストを置くと、Quint B とほぼ同じだけ効いた

- if 文版 × Haiku は 1/35 → 31/35。Sonnet は 23/35 → 35/35。
- rel 版は Haiku も Sonnet も 35/35。
- 降格系（ロール変更、メンバー削除、オフボード、一括ロール変更、メンバー移動）は、①の4セルすべてで 5/5 だった。
- 残った失敗は、v2 × Haiku の移動（4本）と凍結（4本）。

### 2. チェックが実際に落ちたのは1本だけ。効いたのは「規則が読めること」

- ヘルパーのある320本（①③）は、すべて作業中に `rules_test.go` を読んでいた。
- エージェントが書いた新しいテストは、すべて `do()` を通していた。チェックを迂回した試行はない。
- 一方で、途中の `go test` で規則のチェックが失敗したのは 320本中1本（1470）だけだった。
  - 会話記録から数えた（`results/invtest-rulecheck-hits.tsv`）。
- つまりエージェントは、テストに落とされてから直したのではない。先に規則を読み、それを守るように実装した。
- 効き方は「テストが失敗を捕まえた」ではなく、「規則がコード（SQL）として書かれていて、読めた」である。
  - README に不変条件を書いた実験（実験 08）や、Quint B の「反例をほとんど見ていない」と同じ構図である。

### 3. テストが捕まえるのは、エージェントが試した場面だけ（移動）

- v2 × Haiku の移動は、①で 4/5、③で 4/5 が漏れた。
  - 落ちたのは、ivy（manager）が担当のタスクを、ivy が書き込めないプロジェクトへ移すケース。
- エージェントのテストは、この場面を作っていなかった。そのためヘルパーは何も検出しなかった。
- `do()` の後のチェックは、テストが通った書き込みの結果しか見ない。誰が担当のときに何をするか、という場面を思いつかなければ、捕まえられない。

### 4. 凍結: 7本がヘルパーの規則を書き換えて、すべて失敗した

①③の凍結40本の内訳（差分から分類）:

| 行動 | 本数 | authz_ok |
|---|---|---|
| 担当を外した | 33 | 33 |
| `rules_test.go` の規則を緩めた（凍結中のプロジェクトは対象外にする） | 7 | 0 |
| 凍結を拒否した | 0 | — |

- 規則を緩めた7本は、すべて Haiku だった（1468、1469、1470、1472、1508、1789、1792）。
  - v2 × Haiku は5本中4本が緩めた。
  - Sonnet は40本中0本。
- チェックの失敗を見てから緩めたのは 1470 の1本だけ。残りの6本は、規則を読んだ時点で「凍結すると全員 viewer になるので、この規則と衝突する」と判断し、先回りして例外を足した。
- 1477（transfer）は規則を緩めたのではなく、規則を1つ足した。
- Quint の凍結でも、不変条件を緩めた8本のうち6本が反例を見る前だった。同じ傾向である。
- 人に判断を返した試行は数えていない。トライアルは自律実行で、480本すべてがコミットして終わった。

### 5. TDD だけでは効かなかった

- ② TDD は、最初の比較とほぼ同じ。
  - v2 × Haiku 1 → 2/35、v2 × Sonnet 23 → 22/35、rel × Haiku 29 → 31/35。
  - 凍結は 4セルで 0/5、0/5、0/5、2/5。
- 先に書いたテスト（1つ目のコミット）の中身。キーワードによる推定で、`results/tdd-first-commit-tests.tsv` にある。
  - 拒否側のケース（403/404）は、320本すべてにあった。
  - 担当の後始末を確かめるテストは、降格系・移動・凍結で次の本数だった。
    - v2 × Haiku 1/30、v2 × Sonnet 14/30
    - rel × Haiku 15/30、rel × Sonnet 21/30
  - 担当の後始末をテストした試行は、ほとんどが authz_ok だった。
- 先に書くテストは、エージェントがすでに理解している範囲を写すだけである。不変条件に気づいていなければ、テストにも出てこない。
  - 実験 09 で「テーブルテストの行が実装を写していた」のと同じである。

### 6. 拒否しすぎは、どの条件でも減らなかった

- 7タスク合計の拒否しすぎ: 最初の比較 16、① 15、② 18、③ 12。
- ③ は少し減ったが、移動で安全かつ動いたのは各セル 1/5 にとどまった。
- TDD で先に書いた移動のテストに「contributor が自分のタスクを移せる（200）」というケースがあったのは、次の本数だけだった。
  - ② Haiku 1/10、Sonnet 0/10
  - ③ Haiku 4/10、Sonnet 2/10
- 多くの試行は、manager 限定をテストの期待値として先に書いていた。テストが拒否しすぎを固定する側に働いた。
- 拒否しすぎが減ったのは、今のところ「関係メソッド版 + タスク文で許可側を明示する」組み合わせだけである（実験 10）。

## 注意

- 不変条件のチェックは、採点器の ATOM（担当者の規則とメンバーの組織の規則）とほぼ同じ内容である。正解に近い情報を渡している。
  - 特に v2 では、README にない規則を、テストの形で初めて渡している。
- ①の効果は「テストが失敗を捕まえた」効果ではない。チェックが失敗したのは320本中1本だけで、効いたのは「規則が読めること」である（結果2）。
  - 規則を README にだけ書いた v2（実験 08、606〜625）とは、降格系の2タスクでしか比べられない。
- 会話記録から数えた集計（チェックの失敗、`rules_test.go` を読んだか）は、会話記録を公開しないため、表としてだけ残す。
- TDD のテストの中身は、キーワードによる推定である。
- 各セルは n=5。1〜2本の差はノイズとみなす。
