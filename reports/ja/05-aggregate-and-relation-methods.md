# 集約版の結果: Active Record + 操作ごとの集約、全体チェックなし（2026-11-23）

## fixture

`fixture/taskboard-agg` は、実運用の構成に寄せた tanukirpc 版である。

**tanukirpc 版（`taskboard-cap`）と同じ部分**
- tanukirpc の層（`main.go`）
- scope と capability の API
- tx による「全部成功か、全部なしか」の性質

**変えた部分**
- `record.go`: Active Record 風のデータ層。テーブルごとの Record 型、tx 上の finder、`save` と `destroy` からなる。
- `aggregate.go`: 操作ごとの集約。各集約は、その操作に必要なレコードを読み込み、その操作に関わるルールだけを検査して保存する。
- 全体の `state.check()` はない。
- Task は担当者を `AssigneeID string` で持つ。
- README はモデルのルール（不変条件）を記述しているが、実装方法の指示（「To add a feature」）は含まない。

**同等性**: 8つの凍結済み採点器すべてで、落ちるサブテストの集合が if 文版、tanukirpc 版と一致した（`results/structure/equivalence-agg/`）。

## 結果（Haiku、各5本、トライアル 321〜360、40本すべて valid_run）

| タスク | Haiku if | Haiku cap | **Haiku agg** | agg での守られ方 |
|---|---|---|---|---|
| 移動 | 0 | 5 | **5** | 移動用の集約が、移動先での担当者のロールを確認した |
| ロール変更 | 0 | 5 | **3** | 327〜329 は、本人の担当タスクを集約に読み込み、viewer への降格を拒否した。326 と 330 は Membership だけを読み込んだので、担当が残った |
| メンバー削除 | 0 | 5 | **5** | 担当を明示的に整理した |
| 組織からの除外 | 0 | 5 | **5** | 担当を明示的に整理した |
| 移籍 | 0 | 5 | **5** | 担当を整理したもの、またはメンバーシップが残っていれば拒否したもの（349 など） |
| ロール一括変更 | 0 | 5 | **1** | 355 だけが、プロジェクトのタスクを集約に読み込んで検査した。351〜354 は担当者に触れていない |
| メンバー異動 | 0 | 5 | **5** | 担当を明示的に整理した |
| **小計** | **0/35** | **35/35** | **29/35** | |
| 凍結 | 0 | 1 | 0 | 5本とも担当者に触れていない |

**改変の確認**
- 既存の集約（createTask、updateTask、deleteTask）の検査を消した、または弱めたものは0本だった。
- 削除された行は、ルーティングの書き換えと、エラー種別を追加するための `errorHooker` の書き換えだけだった。
- 40本すべてで、REG（既存の振る舞い）の失敗は0件だった。

## 読み取れること

- **全体チェックがないと、降格系が漏れる。** tanukirpc 版でロール変更と一括変更を守っていたのは、`state.check` という安全網だった。集約版にはそれがない。降格系は 4/10 に落ちた（if 文版は 0/10）。
- **漏れ方は、集約に何を読み込むかで決まる。**
  - 成功したトライアルは、集約に「その人の担当タスク」か「プロジェクトのタスク」を読み込んでいた。
  - 失敗したトライアルは、Membership だけを読み込んでいた。
  - つまり、エンティティをまたぐ不変条件は、集約の境界を人が（あるいは AI が）正しく引けたときにだけ守られる。
- **それでも if 文版よりはずっと良い（29/35 対 0/35）。** 削除、除外、移籍、異動、移動は、全体チェックなしでも 25/25 だった。集約という型があり、README にルールが書かれていることで、AI は「この操作が触るレコード」を考えるようになる。
- **交絡**: if 文版の README にはモデルのルールが書かれていない。集約版の README には書かれている。集約という構造の効果と、ルールが文書化されている効果は、まだ分けられていない。

# 関係メソッド版: 実運用の書き方に寄せた集約（2026-11-23）

## fixture

`fixture/taskboard-rel-v1`（このトライアルのベース）は、集約版をもとに、ユーザーの実運用の書き方に寄せたもの。`fixture/taskboard-rel` はこれをさらに書き直した版で、レポート 06 で使った。

- **関係メソッド**: 関連レコードを読み込むメソッドを、レコードに持たせた。
  - `userRecord.Memberships` / `AssignedTasks`
  - `projectRecord.Memberships` / `Membership` / `Tasks`
  - `membershipRecord.Project` / `User` / `AssignedTasks`
  - `taskRecord.Project` / `AssigneeMembership`
- **行メソッド**: 行の変更は、行オブジェクトのメソッドとした（`Create` / `Rename` / `SetStatus` / `Assign` / `Unassign` / `Destroy`）。
- **既存の集約**: 「操作の起点になるレコードから関係メソッドで読み込み、行メソッドで変更する」形に書き直した。
- **全体チェック**: なし。

**設計判断**: `membershipRecord.AssignedTasks` を最初から用意した。I1 を DB で表すと、複合外部キー `tasks(project_id, assignee_id) → memberships` になる。関係から機械的にメソッドを生やすなら、自然に生える関係である。

**同等性**: 8つの採点器すべてで、if 文版と一致した（`results/structure/equivalence-rel/`）。

## 関係メソッドを使ったかどうかと、成否の対応

降格系の10本では、`AssignedTasks` を使ったかどうかと成否が完全に一致した。

| トライアル | 新しく書いた行メソッド | `AssignedTasks` | authz_ok |
|---|---|---|---|
| 366 | `membershipRecord.ChangeRole` | 使わない（`Membership` と `User` のみ） | 不合格 |
| 367〜369 | `ChangeRole` | 使う | 合格 |
| 370 | `SetRole` | 使う | 合格 |
| 391 | `ChangeRole` | 使わない（`Memberships` のみ） | 不合格 |
| 392 | `SetRole` | 使う | 合格 |
| 393、395 | なし / `SetRole` | 使わない（`Memberships` のみ） | 不合格 |
| 394 | `SetRole` | 関係メソッドを1つも使わない | 不合格 |

ほかのタスクでも同じ傾向だった。
- 削除、除外、異動: 15/15 が `AssignedTasks` を使った。
- 移籍: 388 と 389 は使わなかった。代わりに、メンバーシップが残っていれば移籍を拒否する形で守った。
- 凍結: 5本とも `Memberships` だけで、担当者には触れなかった。

## 読み取れること

- **行メソッドのパターンには、ほぼ全員が従った。** 降格系10本のうち9本が、`membershipRecord` に `ChangeRole` か `SetRole` を足した。
- **関係メソッドは、起点からたどる深さが1段なら使われる。**
  - 単体のロール変更は、起点が Membership なので、そこから `AssignedTasks` まで1段。4/5 が使った。
  - 一括変更は、起点が Project なので、`Project → Memberships → AssignedTasks` と2段たどる必要がある。1/5 しか使わなかった。
  - 391、393、395 は `Memberships` までは読み込んだが、その先には進まなかった。
- **パターンは書き方を誘導するが、どこまでたどるかは誘導しない。** 前の集約版（関係メソッドなし）と比べた改善は、ロール変更の +1 だけだった。一括変更は変わらなかった。
